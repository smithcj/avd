# macOS Containerlab Helper — Docker Desktop Enterprise + DoD Iron Bank

This directory contains the alternate Containerlab environment for a macOS workstation running Docker Desktop Enterprise in a restricted environment.

It is intentionally **separate from `.devcontainer/`** so the repository can continue to use Arista's AVD-provided development container when that environment is available.

## Design

The Mac workflow uses Docker-outside-of-Docker (DooD):

```text
macOS
  |
  +-- VS Code
  |
  +-- Docker Desktop Enterprise
        |
        +-- Linux Docker VM
              |
              +-- locally-built Containerlab helper container
              |       |
              |       +-- Docker socket
              |
              +-- cEOS containers
```

Containerlab documents DooD as the preferred devcontainer model when a local macOS or Windows environment needs to use the images and containers already present in the host Docker daemon.

The helper image is built from the DoD Iron Bank UBI 9 image instead of Docker Hub or GHCR.

## Files

```text
mac/
├── README.md
└── Dockerfile
```

Before building, place the approved Linux Containerlab binary in this directory:

```text
mac/
├── README.md
├── Dockerfile
└── containerlab
```

The `containerlab` binary is intentionally not committed to Git.

Add this to the repository `.gitignore`:

```gitignore
# Local Containerlab binary used for restricted Mac build
mac/containerlab
```

## Iron Bank Base Image

The Dockerfile currently uses:

```text
registry1.dso.mil/ironbank/redhat/ubi/ubi9:9.8
```

Verify access from Docker Desktop:

```bash
docker pull registry1.dso.mil/ironbank/redhat/ubi/ubi9:9.8
```

Authentication to `registry1.dso.mil` may be required by the enterprise environment.

## Determine Docker Architecture

The Containerlab binary placed in this directory must be a **Linux** binary matching the architecture used by Docker Desktop.

Check:

```bash
docker version --format '{{.Server.Arch}}'
```

Typical values:

```text
amd64
arm64
```

On Apple Silicon, use the Linux ARM64 Containerlab binary when possible.

On an Intel Mac, use the Linux AMD64 Containerlab binary.

## Containerlab Version

The lab currently uses:

```text
0.79.0
```

Verify the binary before building:

```bash
chmod +x mac/containerlab
mac/containerlab version
```

If that command cannot execute directly on macOS because the supplied file is a Linux binary, verify its type instead:

```bash
file mac/containerlab
```

Example ARM64 result:

```text
ELF 64-bit LSB executable, ARM aarch64
```

Example AMD64 result:

```text
ELF 64-bit LSB executable, x86-64
```

## Build

From the repository root:

```bash
docker build \
  -t avd-containerlab-mac:0.79.0 \
  ./mac
```

This build uses the Iron Bank UBI image and copies the locally supplied Containerlab binary into the image.

It does **not** pull a Containerlab image from GHCR.

Verify:

```bash
docker run --rm \
  avd-containerlab-mac:0.79.0 \
  containerlab version
```

## Running Containerlab

The helper container must use Docker Desktop's Docker daemon rather than starting another Docker daemon.

Containerlab's macOS DooD design requires privileged access and access to Docker's networking state.

A representative invocation from the repository root is:

```bash
docker run --rm -it \
  --privileged \
  --pid=host \
  --network=host \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v /run/docker/netns:/run/docker/netns \
  -v /var/lib/docker:/var/lib/docker \
  -v "$(pwd):$(pwd)" \
  -w "$(pwd)" \
  avd-containerlab-mac:0.79.0 \
  /bin/bash
```

Inside the helper container:

```bash
containerlab version
containerlab deploy -t lab1.clab.yml
```

The same `lab1.clab.yml` used on the Linux server is intended to be reused on the Mac.

## cEOS

Arista cEOS remains a locally imported Docker image:

```bash
docker import cEOS-lab-4.36.2F.tar.xz ceos:4.36.2F
```

Verify:

```bash
docker images | grep ceos
```

Expected:

```text
ceos    4.36.2F
```

Because the Containerlab helper uses Docker Desktop's daemon, it sees the same locally imported cEOS image.

## Relationship to the AVD Devcontainer

This directory does not replace or modify:

```text
.devcontainer/
```

The intended separation is:

```text
repo/
├── .devcontainer/       # Arista AVD development environment
├── mac/                 # Restricted enterprise-Mac Containerlab helper
│   ├── README.md
│   └── Dockerfile
├── lab1.clab.yml
├── inventory.yml
└── group_vars/
```

On the Linux lab server, Containerlab can run directly on the host while VS Code uses the AVD devcontainer.

On the enterprise Mac, the locally built Iron Bank helper provides Containerlab without requiring access to Containerlab's GHCR devcontainer image.

## Enterprise Restrictions

Docker Desktop Enterprise policy may restrict:

- privileged containers
- Docker socket access
- bind mounts
- host PID mode
- host networking
- Enhanced Container Isolation settings

Containerlab requires privileged Linux networking operations. If enterprise policy blocks these capabilities, this DooD approach will not work and the lab should run on a dedicated Linux VM or server instead.

## Note About Additional Utilities

The Dockerfile is intentionally minimal. It does not use Red Hat package repositories during the build, since those repositories may also be unavailable in the restricted environment.

If Containerlab requires additional Linux utilities in the enterprise environment, they should be supplied through an approved repository or incorporated as approved local artifacts rather than adding unapproved Internet package sources.
